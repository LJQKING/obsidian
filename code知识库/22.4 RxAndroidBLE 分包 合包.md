RxAndroidBLE 本身是一个**RxJava**的封装库，其核心作用是简化蓝牙通信的异步操作，但它**并没有内置**自动分包和合包的逻辑。

这是因为BLE通信的“分包”和“合包”是**应用层协议**的一部分，需要开发者和BLE设备（外设）共同商定一个规则。RxAndroidBLE 提供的是一套**工具**，让你能方便地实现这个商定好的规则。

### 核心概念与原理

分包与合包的必要性源于BLE单次传输数据的长度限制（通常为20字节，可通过协商MTU提升）。

*   **分包 (Splitting)**：在发送端，将长数据按**应用层协议**（如自定义头部+数据体）拆分成多个符合MTU大小的小包，然后依次发送。
*   **合包 (Merging)**：在接收端，根据**同样的协议**，将接收到的多个小包重新组合成完整数据。

这个过程中，数据包的“身份”至关重要。常见的分包协议有以下几种：

| 策略 | 实现方式 | 优点 | 缺点 |
| :--- | :--- | :--- | :--- |
| **基于标志位 (Flag-Based)** | 在每个包开头添加一个字节的标志（如`0x01`表示开始，`0x02`表示中间，`0x03`表示结束）。 | 实现简单，接收端可根据标志实时处理。 | 若中间包丢失，整个消息将无法重组。 |
| **基于头部 (Header-Based)** | 在**第一个包**的头部写入整个消息的总长度（如2字节）。后续包只包含数据。 | 接收端能预先知道总大小，便于分配内存和校验完整性。 | 实现略复杂，需要处理首包和后续包的逻辑。 |
| **基于序号 (Sequence-Based)** | 在每个包的头部写入**总包数**和**当前包序号**。 | 即使包乱序到达，也能正确重组，可靠性高。 | 头部开销较大。 |

### 具体场景代码示例

以下代码演示了在RxAndroidBLE中如何实现“基于头部”的分包发送和接收。

#### 1. 发送端：分包逻辑
假设已通过`requestMtu(512)`将MTU协商为512字节。

```java
// 假设 mtu = 512, 实际可用payload = 512 - 头部长度(2)
private byte[][] splitData(byte[] data, int mtu) {
    int headerSize = 2; // 用于存放总长度的头部
    int payloadSize = mtu - headerSize;
    int totalPackets = (int) Math.ceil(data.length / (double) payloadSize);
    byte[][] packets = new byte[totalPackets][];

    for (int i = 0; i < totalPackets; i++) {
        int start = i * payloadSize;
        int length = Math.min(payloadSize, data.length - start);
        // 1. 创建包：总长度 = 头部(2) + 数据体
        byte[] packet = new byte[headerSize + length];
        // 2. 写入头部：整个消息的总长度 (大端序)
        packet[0] = (byte) (data.length >> 8);
        packet[1] = (byte) (data.length & 0xFF);
        // 3. 写入数据体
        System.arraycopy(data, start, packet, headerSize, length);
        packets[i] = packet;
    }
    return packets;
}
```

#### 2. 使用RxAndroidBLE发送
关键在于使用 **`concatMap`** 操作符，它能确保**一个包发送完成后，再发送下一个包**，避免数据“ flooding ”导致设备无法处理。

```java
byte[] longData = ...; // 待发送的长数据
int mtu = 512; // 协商后的MTU
byte[][] packets = splitData(longData, mtu);

rxBleConnection
    .writeCharacteristic(characteristicUuid, new byte[0]) // 仅用于获取Observable
    .flatMap(ignored -> Observable.fromArray(packets)) // 将packets数组转为流
    .concatMap(packet -> 
        rxBleConnection.writeCharacteristic(characteristicUuid, packet)
                      .doOnNext(bytes -> Log.d("TAG", "分包发送成功"))
    )
    .ignoreElements() // 只关心完成事件
    .doOnComplete(() -> Log.d("TAG", "所有分包发送完成"))
    .subscribe(
        () -> { /* 全部发送成功 */ },
        throwable -> { /* 处理错误 */ }
    );
```
`concatMap` 保证了写入的顺序性，而 `ignoreElements()` 则让你能监听“所有分包发送完成”这一整体事件。

#### 3. 接收端：合包逻辑
接收端需要根据相同的头部协议，将数据包重新组合。

```java
// 假设这是从 Notification 中收到的数据包
private byte[] mergedData = null;
private int expectedTotalLen = -1;
private ByteArrayOutputStream baos = new ByteArrayOutputStream();

public void onPacketReceived(byte[] packet) {
    if (expectedTotalLen == -1 && packet.length >= 2) {
        // 1. 解析第一个包的头部的总长度
        expectedTotalLen = ((packet[0] & 0xFF) << 8) | (packet[1] & 0xFF);
        // 2. 跳过头部，写入数据体
        baos.write(packet, 2, packet.length - 2);
    } else {
        // 3. 后续包直接写入数据体
        baos.write(packet, 0, packet.length);
    }

    // 4. 检查是否收齐
    if (baos.size() == expectedTotalLen) {
        mergedData = baos.toByteArray(); // 完整数据
        // 处理完整数据...
        reset(); // 重置状态，准备接收下一条消息
    }
}
```

### 如何确认包发送成功

在BLE中，“包发送成功”分为两个层面：

1.  **硬件层确认**：操作成功，数据已从手机发出。
2.  **应用层确认**：数据不仅发出，还被外设正确接收和处理。

#### 硬件层确认
RxAndroidBle的`writeCharacteristic`方法返回的`Single<byte[]>`，其`onSuccess`回调即表示**硬件层写入成功**。

```java
rxBleConnection.writeCharacteristic(uuid, packet)
    .subscribe(
        bytes -> { 
            // 1. 硬件层确认：此包已成功写入手机的发送队列
        },
        throwable -> { 
            // 处理写入失败
        }
    );
```

#### 应用层确认（推荐）
更可靠的做法是，由外设处理完数据后，通过另一个“通知（Notification）”特征，回复一个**应用层ACK（确认）包**。

```java
// 在建立连接时，先订阅外设的“通知”特征
rxBleConnection.setupNotification(ackCharacteristicUuid)
    .flatMap(notificationObservable -> notificationObservable)
    .subscribe(
        ackData -> {
            // 2. 应用层确认：外设回复了ACK，表示数据处理完毕
            if (isValidAck(ackData)) {
                // 可以安全地发送下一个数据包了
            }
        },
        throwable -> { /* 处理错误 */ }
    );
```

**在实际开发中，强烈建议采用“应用层确认”机制**，这是确保BLE通信可靠性的最佳实践。

### 总结

| 问题 | 解决方案 | 关键点 |
| :--- | :--- | :--- |
| **如何分包？** | 应用层协议，如**头部+数据体**结构。 | 头部包含数据总长度或包序号。 |
| **如何合包？** | 接收端解析头部，将数据体**按序拼接**。 | 维护一个缓冲区，直到收齐所有数据。 |
| **如何保证顺序发送？** | 使用RxJava的 **`concatMap`** 操作符。 | 确保上一个包写入完成后，才处理下一个。 |
| **如何确认发送成功？** | **硬件层**看`writeCharacteristic`的回调；**应用层**依赖外设的**ACK通知**。 | 应用层ACK是可靠通信的保障。 |
