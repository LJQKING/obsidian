
### 方案一：`removeCallbacksAndMessages(null)`（最基础，简单场景）
适用于只有少量延迟消息且能保证在生命周期结束前全部移除的情况。
```kotlin
class SpeedActivity : AppCompatActivity() {
    // 非静态内部类，默认持有外部Activity引用
    private val handler = Handler(Looper.getMainLooper()) { msg ->
        // 处理消息，可能访问Activity的View
        true
    }

    override fun onDestroy() {
        super.onDestroy()
        // 移除所有回调和消息，断开引用链
        handler.removeCallbacksAndMessages(null)
    }
}
```
**缺点**：如果忘记调用 `removeCallbacksAndMessages`，或者某些回调在 `onDestroy` 之后还被触发（如 Binder 回调抛出 Runnable），仍可能泄漏。

---

### 方案二：静态内部类 + `WeakReference`（通用且彻底）
彻底断绝 Handler 对 Activity 的强引用，即使消息未处理完，Activity 也可被 GC 回收。
```kotlin
class SpeedActivity : AppCompatActivity() {
    // 静态内部类，不持有外部引用
    private val handler = SpeedHandler(this)

    override fun onDestroy() {
        super.onDestroy()
        handler.removeCallbacksAndMessages(null)
    }

    // 定义静态类，使用WeakReference持有Activity
    class SpeedHandler(activity: SpeedActivity) : Handler(Looper.getMainLooper()) {
        private val activityRef = WeakReference(activity)

        override fun handleMessage(msg: Message) {
            activityRef.get()?.let { act ->
                // 安全访问 Activity 中的 View
                when (msg.what) {
                    MSG_UPDATE_SPEED -> {
                        val speed = msg.obj as Float
                        act.speedGaugeView.setSpeed(speed)
                    }
                }
            }
        }
    }

    companion object {
        const val MSG_UPDATE_SPEED = 1
    }
}
```
**关键点**：
- `SpeedHandler` 是静态内部类，不隐含持有外部类引用。
- 通过 `WeakReference` 获取 Activity，即使 Activity 被销毁，`activityRef.get()` 返回 `null`，后续操作被自动忽略，不会 NPE（前提是不在 `null` 时调用方法）。
- 仍建议在 `onDestroy` 中 `removeCallbacksAndMessages(null)` 避免执行无用代码。

**车载场景适应**：若 Binder 回调在 Activity 销毁后仍通过 Handler 投递消息，`WeakReference` 确保 Activity 能被回收，消息处理变为空操作。

---

### 方案三：Handler 放入 `ViewModel` + `LiveData/Flow`（生命周期感知，推荐）
将数据接收与 UI 彻底解耦：Handler 在 ViewModel 中运行，通过 `LiveData` 或 `StateFlow` 通知 UI，利用生命周期感知组件自动停止更新。
```kotlin
class SpeedViewModel : ViewModel() {
    private val _speed = MutableLiveData<Float>()
    val speed: LiveData<Float> = _speed

    // Handler 持有 ViewModel 的引用，ViewModel 的生命周期由系统管理
    // 即使 Handler 持有 ViewModel，因 ViewModel 没有持有 Activity/View，
    // Activity 回收时 ViewModel 仍存活直到 onCleared，但不会导致 View 泄漏
    private val handler = Handler(Looper.getMainLooper()) { msg ->
        when (msg.what) {
            MSG_UPDATE_SPEED -> {
                val speedValue = msg.obj as Float
                _speed.value = speedValue   // 数据驱动 UI 更新
                true
            }
            else -> false
        }
    }

    // 对外提供方法，供外部（如Binder回调）调用
    fun postSpeedUpdate(speed: Float) {
        // 通过Handler切换到主线程
        handler.obtainMessage(MSG_UPDATE_SPEED, speed).sendToTarget()
    }

    override fun onCleared() {
        super.onCleared()
        handler.removeCallbacksAndMessages(null)  // 清理资源
    }

    companion object {
        const val MSG_UPDATE_SPEED = 1
    }
}

// Activity/Fragment 中安全观察
class SpeedActivity : AppCompatActivity() {
    private val viewModel: SpeedViewModel by viewModels()

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        // 观察 LiveData，生命周期感知，销毁时自动移除观察者
        viewModel.speed.observe(this) { speed ->
            speedGaugeView.setSpeed(speed)
        }
    }
}
```
**优势**：
- **彻底分离 View**：Handler 不持有 Activity/Fragment 引用，完全不存在 View 泄露。
- **自动生命周期管理**：`LiveData.observe` 会在 Activity 销毁时自动取消订阅，不会收到过期数据。
- **符合架构设计**：符合 MVVM 思想，可单元测试。

**车载场景适配**：
- `CarPropertyManager` 的 Binder 回调在后台线程，可直接调用 `viewModel.postSpeedUpdate(speed)`，ViewModel 内部的 Handler 切换到主线程并更新 `LiveData`。
- 若需要处理复杂异步流，可将 `handler` 替换为 `viewModelScope.launch(Dispatchers.Main)` 直接更新 `StateFlow`。

---

### 总结对比
| 方案 | 内存泄漏风险 | 代码复杂度 | 推荐场景 |
|------|--------------|------------|----------|
| `removeCallbacks` | 中（依赖手动调用） | 低 | 简单一次性消息 |
| 静态内部类 + WeakReference | 低 | 中 | 需要直接操作 View 且无法迁移到 MVVM 的老代码 |
| ViewModel + LiveData/Flow | 无 | 中 | **量产项目首选**，彻底解耦，天然适配生命周期 |

当前座舱开发已普遍采用 ViewModel 方案，推荐优先使用。
