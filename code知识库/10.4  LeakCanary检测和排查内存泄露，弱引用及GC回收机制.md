我来为你深入讲解 LeakCanary、内存泄漏检测、弱引用和 GC 回收机制。这对面试准备非常重要。## LeakCanary 工作原理详解

### 核心工作步骤

**1. 生命周期监听阶段** LeakCanary 通过 `LifecycleWatcher` 接口监听 Activity 和 Fragment 的销毁事件。在 Android 中，当 Activity 被销毁后（`onDestroy()` 调用），应该完全释放内存。

```kotlin
// LeakCanary 的原理（简化版）
class LifecycleWatcher {
    private val watchedReferences = mutableMapOf<String, WeakReference<Any>>()
    
    fun watch(objectToWatch: Any, description: String) {
        // 将对象用弱引用包装
        watchedReferences[description] = WeakReference(objectToWatch)
    }
}
```

**2. 弱引用与垃圾回收机制**

弱引用是理解 LeakCanary 的关键。Java 的引用类型有四种：

|引用类型|GC 表现|使用场景|
|---|---|---|
|**强引用**|GC 不会回收|普通对象引用|
|**软引用**|内存不足时回收|缓存|
|**弱引用**|GC 立即回收|监听已销毁的对象|
|**虚引用**|无引用作用，仅通知|追踪对象回收过程|

```kotlin
// 弱引用的核心特性
val activity = Activity()
val weakRef = WeakReference(activity)

// 正常情况：引用存在
println(weakRef.get()) // Activity@1234

// 手动清空强引用 + 触发 GC
activity = null
System.gc()

// GC 后，弱引用自动清空
println(weakRef.get()) // null
```

**3. GC 回收机制与泄漏判断**

```kotlin
// 简化的 LeakCanary 检测流程
object LeakDetector {
    fun detectLeak(activity: Activity) {
        val weakRef = WeakReference(activity)
        
        // 第一步：延迟等待（给 GC 机会）
        Thread.sleep(5000)
        
        // 第二步：强制触发 GC
        System.gc()
        Thread.sleep(100)
        Runtime.getRuntime().gc()
        
        // 第三步：检查引用是否被清空
        if (weakRef.get() != null) {
            // ❌ 泄漏！对象依然存活
            // 生成 Heap Dump 进行分析
            Debug.dumpHprofData("/data/anr/leak.hprof")
            analyzeLeak()
        } else {
            // ✓ 无泄漏，对象已被回收
            println("Activity 正常释放")
        }
    }
}
```

## 常见内存泄漏及其排查

### 场景 1：静态引用（最常见）

```kotlin
class MyActivity : AppCompatActivity() {
    companion object {
        // ❌ 泄漏：静态引用持久存活
        var instance: MyActivity? = null
    }
    
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        instance = this  // Activity 被静态引用捕获
    }
    
    override fun onDestroy() {
        super.onDestroy()
        // ❌ 如果这里不清空，Activity 永远无法回收
        // instance = null
    }
}

// ✓ 改进方案
class MyActivity : AppCompatActivity() {
    companion object {
        var instance: WeakReference<MyActivity>? = null
    }
    
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        instance = WeakReference(this)  // 用弱引用包装
    }
}
```

### 场景 2：内部类隐式引用

```kotlin
class MyActivity : AppCompatActivity() {
    private val handler = Handler(Looper.getMainLooper()) {
        // ❌ 泄漏：Handler 是非静态内部类
        // 隐式持有 MyActivity 的引用（通过 this@MyActivity）
        updateUI()
        true
    }
    
    override fun onDestroy() {
        super.onDestroy()
        // ❌ 如果不移除消息，Activity 无法回收
    }
}

// ✓ 改进方案 1：使用静态内部类 + WeakReference
class MyActivity : AppCompatActivity() {
    private val handler = SafeHandler(this)
    
    override fun onDestroy() {
        super.onDestroy()
        handler.removeCallbacksAndMessages(null)  // 清空消息队列
    }
    
    companion object {
        private class SafeHandler(activity: MyActivity) 
            : Handler(Looper.getMainLooper()) {
            private val activityRef = WeakReference(activity)
            
            override fun handleMessage(msg: Message) {
                val activity = activityRef.get() ?: return
                activity.updateUI()
            }
        }
    }
}

// ✓ 改进方案 2：使用协程（推荐）
class MyActivity : AppCompatActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        lifecycleScope.launchWhenStarted {
            delay(1000)
            updateUI()  // 协程自动感知生命周期
        }
    }
    
    override fun onDestroy() {
        super.onDestroy()
        // 协程会自动取消，不需要手动清理
    }
}
```

### 场景 3：监听器和回调未注销

```kotlin
class MyActivity : AppCompatActivity(), SensorEventListener {
    private lateinit var sensorManager: SensorManager
    
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        sensorManager = getSystemService(SENSOR_SERVICE) as SensorManager
        
        // ❌ 泄漏：注册了监听器但未注销
        val sensor = sensorManager.getDefaultSensor(Sensor.TYPE_ACCELEROMETER)
        sensorManager.registerListener(this, sensor, SensorManager.SENSOR_DELAY_NORMAL)
    }
    
    override fun onDestroy() {
        super.onDestroy()
        // ❌ 如果这里不注销，Activity 被监听器持有
        // sensorManager.unregisterListener(this)  // 必须调用
    }
}

// ✓ 改进方案
class MyActivity : AppCompatActivity(), SensorEventListener {
    private lateinit var sensorManager: SensorManager
    
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        sensorManager = getSystemService(SENSOR_SERVICE) as SensorManager
        val sensor = sensorManager.getDefaultSensor(Sensor.TYPE_ACCELEROMETER)
        sensorManager.registerListener(this, sensor, SensorManager.SENSOR_DELAY_NORMAL)
    }
    
    override fun onPause() {
        super.onPause()
        sensorManager.unregisterListener(this)  // 在 onPause 中注销
    }
    
    override fun onResume() {
        super.onResume()
        val sensor = sensorManager.getDefaultSensor(Sensor.TYPE_ACCELEROMETER)
        sensorManager.registerListener(this, sensor, SensorManager.SENSOR_DELAY_NORMAL)
    }
}
```

## 弱引用与 GC 的深度理解

```kotlin
// GC 回收过程的可视化模拟

// 场景 1：强引用阻止 GC
class LargeObject(val data: ByteArray = ByteArray(1024 * 1024))

fun strongReferenceExample() {
    var obj = LargeObject()      // 创建对象，强引用指向它
    System.gc()
    println("对象仍在内存中: ${obj != null}")  // true，GC 无法回收
}

// 场景 2：弱引用允许 GC
fun weakReferenceExample() {
    var obj: LargeObject? = LargeObject()
    val weakRef = WeakReference(obj)          // 弱引用包装
    
    println("回收前: ${weakRef.get() != null}")  // true
    
    obj = null                                 // 清空强引用
    System.gc()
    
    println("回收后: ${weakRef.get() != null}")  // false，GC 已回收
}

// 场景 3：GC Root 分析
/**
 * GC Root 是垃圾回收的起点，包括：
 * 1. 虚拟机栈中的本地变量表引用的对象
 * 2. 方法区中的类静态属性引用的对象
 * 3. 方法区中的常量引用的对象
 * 4. JNI 本地方法栈中 JNI 引用的对象
 * 5. 虚拟机内部引用（Class、Exception、Thread 等）
 */

// ❌ 泄漏场景：静态引用形成 GC Root
object AppState {
    var currentActivity: Activity? = null  // 静态引用 = GC Root
}

// Activity 销毁后，AppState.currentActivity 仍指向它
// GC 沿着"GC Root -> AppState -> Activity"的路径，认为 Activity 仍被引用

// 修复：使用弱引用打断引用链
object AppState {
    var currentActivityRef: WeakReference<Activity>? = null
    
    fun getCurrentActivity(): Activity? = currentActivityRef?.get()
}

// 现在 GC 路径变为：GC Root -> WeakReference（可忽略）-> Activity
// GC 会忽略弱引用，直接回收 Activity
```

## LeakCanary 在实际开发中的使用

### 集成和配置

```kotlin
// build.gradle
dependencies {
    debugImplementation 'com.squareup.leakcanary:leakcanary-android:2.14'
}

// LeakCanary 会自动初始化（无需手动配置）
// 但可以自定义配置
class MyApplication : Application() {
    override fun onCreate() {
        super.onCreate()
        
        // 自定义 LeakCanary 行为
        LeakCanary.config = LeakCanary.config.copy(
            retainedVisibleThreshold = 5,  // 保留多少个泄漏后才报警
            dumpHeapWhenDebugging = true,  // 调试时生成 Heap Dump
            excludedRefs = setOf(
                "com.example.app.MyClass.instance"  // 排除某些已知的误报
            )
        )
    }
}
```

### Heap Dump 分析工具链

```bash
# LeakCanary 生成的 .hprof 文件可用 Android Studio 分析

# 1. 转换格式（Android .hprof -> Java .hprof）
hprof-conv leak.hprof leak-converted.hprof

# 2. 用 JProfiler 或 MAT（Memory Analyzer Tool）打开
# - 定位泄漏对象
# - 查看 GC Root 到对象的引用链
# - 识别最短保留路径（Shortest Retain Path）

# 3. 使用 Android Studio 的 Profiler
# 菜单：View > Tool Windows > Profiler
# - 选择内存标签页（Memory）
# - 点击"Dump Java Heap"生成快照
# - 按"Unreachable"过滤找到泄漏对象
```

## 面试核心问题速查

|问题|核心答案|
|---|---|
|LeakCanary 如何工作？|WeakReference + Heap Dump + 引用链分析|
|为什么用弱引用？|允许 GC 回收，不阻断垃圾回收过程|
|如何判断是否泄漏？|Activity 销毁后，引用仍不为 null，且强制 GC 后仍存在|
|最常见的泄漏原因？|静态引用、内部类、未注销回调、资源未释放|
|GC Root 是什么？|垃圾回收的起点，包括栈变量、静态变量、本地引用等|
|如何修复泄漏？|打断引用链、及时注销回调、使用弱引用/生命周期感知|
|Handler 为何导致泄漏？|非静态内部类隐式持有外部类引用 + 消息队列延迟执行|
