
### 一、线程池是什么

- [[5.5  线程池与源码对照.md]]  线程池
**线程池（ThreadPoolExecutor）** 是 Java 并发包（`java.util.concurrent`）中提供的一种**管理和复用线程的资源池**。

在 Android 开发中，线程池主要解决三个痛点：**减少线程创建销毁的开销**、**控制并发线程数量**（避免 CPU 资源耗尽导致卡顿）、**统一管理后台任务**。

**核心本质**：线程池的核心是 **“池化技术”** 。它在内部维护了一组工作线程（Worker），并借助一个**阻塞队列（BlockingQueue）**来存放待执行的任务。池中的线程会不断从队列中取出任务执行，执行完一个任务后不会销毁，而是去取下一个任务，从而实现线程复用。

### 二、创建方式及核心区别

线程池**没有“启动”这个动作**，只有 **“创建（实例化）”** 和 **“提交任务（执行）”**。创建方式主要分为两大类，它们的核心参数决定了性能和行为差异。

#### 1. 创建方式对比（`Executors` 工厂 vs 自定义构造）

| 创建方式 | 对应方法 | 核心参数 (核心/最大/队列) | 特点 | **致命风险 (Android)** |
| :--- | :--- | :--- | :--- | :--- |
| **固定线程池** | `Executors.newFixedThreadPool(n)` | n / n / **无界队列** | 线程数固定，稳定处理突发负载 | **队列无界**，任务堆积过多会导致 **OOM** |
| **缓存线程池** | `Executors.newCachedThreadPool()` | 0 / 极大(Int.MAX) / **同步移交队列** | 任务到达即建线程，空闲60s回收 | **线程数无上限**，瞬间大流量会创建大量线程，导致 CPU 满载或 OOM |
| **单一线程池** | `Executors.newSingleThreadExecutor()` | 1 / 1 / **无界队列** | 保证任务**串行**执行（FIFO） | 同 Fixed，无界队列存在 OOM 隐患 |
| **定时线程池** | `Executors.newScheduledThreadPool(n)` | n / 极大 / 延迟队列 | 支持延时执行和周期性执行 | 线程数无上限 + 队列无界，双重 OOM 风险 |
| **手动定制（推荐）** | **`new ThreadPoolExecutor(...)`** | **开发者自定义** | 参数全透明，可控 | **无风险**（合理配置下），官方强烈推荐 |

> **Android 官方明确警告**：`Executors` 工厂类中的 `newFixedThreadPool` 和 `newCachedThreadPool` 由于未限制队列容量或线程数，在移动设备上极易引发内存溢出（OOM），**强烈建议直接使用 `ThreadPoolExecutor` 的构造函数手动配置**。

#### 2. 任务提交方式区别（`execute()` vs `submit()`）

| 提交方法 | 参数类型 | 返回值 | 异常捕获 | 适用场景 |
| :--- | :--- | :--- | :--- | :--- |
| **`execute(Runnable)`** | `Runnable` | **无**（`void`） | 异常会在线程池内部打印，调用方**无法捕获** | 执行“触发即忘”的异步任务（如埋点日志写入） |
| **`submit(Callable/T)`** | `Runnable` 或 `Callable` | **`Future<T>`** | 通过 `Future.get()` 可捕获 `ExecutionException` | 需要获取执行结果或处理异常的场景 |

### 三、具体场景代码实现

#### 场景：Android 网络请求 + 数据库批量存储（手动定制线程池）

```java
// 1. 在 Application 或单例中定义一个全局线程池
public class AppExecutors {
    private static final int CPU_COUNT = Runtime.getRuntime().availableProcessors();
    private static final int CORE_POOL_SIZE = CPU_COUNT + 1;      // 核心线程数
    private static final int MAX_POOL_SIZE = CPU_COUNT * 2 + 1;   // 最大线程数
    private static final int KEEP_ALIVE_TIME = 30;                // 空闲存活时间（秒）

    private final ThreadPoolExecutor mNetworkExecutor;

    private AppExecutors() {
        mNetworkExecutor = new ThreadPoolExecutor(
                CORE_POOL_SIZE,                  // 核心线程数
                MAX_POOL_SIZE,                   // 最大线程数
                KEEP_ALIVE_TIME,                 // 超时时间
                TimeUnit.SECONDS,                // 超时单位
                new ArrayBlockingQueue<>(128),   // 有界阻塞队列（防止 OOM）
                new ThreadPoolExecutor.DiscardPolicy() // 队列满时丢弃任务，不抛异常
        );
    }

    // 单例获取
    public static AppExecutors getInstance() { return SingletonHolder.INSTANCE; }
    private static class SingletonHolder { private static final AppExecutors INSTANCE = new AppExecutors(); }

    // 供外部调用的执行方法
    public void execute(Runnable task) {
        mNetworkExecutor.execute(task);
    }

    // 提交带返回值的任务
    public <T> Future<T> submit(Callable<T> task) {
        return mNetworkExecutor.submit(task);
    }

    // 安全关闭（在 Application 的 onTerminate 或退出时调用）
    public void shutdown() {
        mNetworkExecutor.shutdown(); // 不再接受新任务，执行完现有任务后关闭
        // 或使用 shutdownNow() 强制立即停止
    }
}

// 2. 在 Activity 中使用
public class MainActivity extends AppCompatActivity {
    public void fetchData(View view) {
        // 执行无返回值任务（网络请求）
        AppExecutors.getInstance().execute(() -> {
            // 此处运行在子线程
            String result = httpGet("https://api.example.com/data");
            runOnUiThread(() -> textView.setText(result));
        });

        // 执行有返回值任务（计算结果）
        Future<Integer> future = AppExecutors.getInstance().submit(() -> {
            Thread.sleep(1000);
            return 1 + 2;
        });
        // 注意：future.get() 会阻塞当前线程，不要在主线程调用！
    }
}
```

### 四、实现原理（核心执行流程）

线程池的核心逻辑封装在 `ThreadPoolExecutor.execute()` 方法中，其流转机制遵循经典的 **“核心 -> 队列 -> 最大 -> 拒绝”** 四级策略：

#### 1. 任务提交时的执行策略（流程图逻辑）

当调用 `execute(Runnable command)` 时，线程池按以下顺序决策：

1. **判断核心线程数（Core Pool）**：
   - 如果当前工作线程数 < `corePoolSize`，**立即创建新线程**执行该任务（即使有其他空闲线程也不复用）。
2. **判断阻塞队列（Blocking Queue）**：
   - 如果核心线程已满，尝试将任务 **放入工作队列**（`workQueue.offer(command)`）。如果入队成功，任务等待空闲线程获取。
3. **判断最大线程数（Maximum Pool）**：
   - 如果队列已满（`offer` 返回 `false`），检查当前线程数是否 < `maximumPoolSize`。如果是，**创建非核心线程**执行该任务。
4. **执行拒绝策略（Reject Policy）**：
   - 如果线程数已达到 `maximumPoolSize`，则执行拒绝策略（默认是 `AbortPolicy`，直接抛出 `RejectedExecutionException`）。

> **关键点**：**先判断核心线程是否满，再入队；队列满后才创建非核心线程**。这意味着非核心线程通常只在任务突发、队列积压时才会被创建。

#### 2. 线程复用原理（Worker 机制）

- 线程池内部的每个工作线程被封装为 **`Worker`** 对象（继承自 `AbstractQueuedSynchronizer`，即 AQS）。
- Worker 启动后，会不断执行一个死循环：
  ```java
  while (task != null || (task = getTask()) != null) {
      task.run(); // 执行任务
      task = null;
  }
  ```
- **`getTask()`** 方法会从阻塞队列中取任务：
  - 如果当前工作线程数 > `corePoolSize`，`getTask()` 会调用 `poll(keepAliveTime, TimeUnit)` 超时等待。若超时未获取到新任务，该 Worker 会被回收（线程销毁）。
  - 如果当前工作线程数 ≤ `corePoolSize`，`getTask()` 会调用 `take()` 无限阻塞，直到有新任务到达，确保核心线程永远存活。

#### 3. 核心状态控制（`ctl` 原子变量）

线程池使用一个 **`AtomicInteger` 类型的 `ctl`** 变量同时存储两个信息：
- **高 3 位**：线程池运行状态（`RUNNING`、`SHUTDOWN`、`STOP`、`TIDYING`、`TERMINATED`）。
- **低 29 位**：当前有效工作线程数（`workerCount`）。

### 五、重要补充与最佳实践

- **队列选择**：
  - **`ArrayBlockingQueue`（有界）**：推荐，防止任务堆积导致 OOM。
  - **`LinkedBlockingQueue`（无界）**：慎用，固定线程池若使用此队列，`maximumPoolSize` 参数将失效。
  - **`SynchronousQueue`（同步移交）**：不存储任务，直接交给线程执行（`newCachedThreadPool` 使用），适合无等待的轻量任务。
- **拒绝策略（RejectedExecutionHandler）**：
  - `AbortPolicy`（默认）：抛异常，适用关键业务（不允许丢任务）。
  - `DiscardPolicy`：静默丢弃，适用不重要的埋点日志。
  - `DiscardOldestPolicy`：丢弃队列最老的任务，再提交当前任务。
  - `CallerRunsPolicy`：由调用方线程（如 UI 线程）执行任务，通过反压减缓任务提交速度。
- **线程命名**：创建自定义线程池时，建议实现 `ThreadFactory` 为线程指定有意义的名字（如 `"Network-Pool-Thread-1"`），便于排查性能问题。
- **AsyncTask 的替代**：Google 已废弃 `AsyncTask`，推荐直接使用 Kotlin 协程（Coroutines）或配合 `LiveData` 的 `ThreadPoolExecutor` 来管理异步任务。
