
### 一、ContentProvider是什么

- [[1.4 ContentProvider 原理.md]]  ContentProvider
ContentProvider（内容提供者）是 Android 四大组件之一，它**对数据提供统一的访问接口**，用于在不同的应用程序（进程）之间**共享数据**。它封装了数据的存取方式（如 SQLite 数据库、文件、网络等），使得外部应用无需关心底层存储细节，只需通过标准的 `Uri`（统一资源标识符）进行增、删、改、查（CRUD）操作。

核心特点：

- **跨进程数据共享**：是 Android 官方推荐的跨应用数据交互标准方案。
- **数据封装与安全**：通过 `Uri` 和权限控制（读写权限），可以精细控制哪些数据允许外部访问。
- **运行在主线程**：ContentProvider 的 `onCreate()`、`query()`、`insert()` 等方法**默认运行在应用的主线程（UI 线程）**。因此，如果外部调用者发起大量数据查询，务必在调用端使用子线程（或 `AsyncQueryHandler`），避免阻塞 UI。

### 二、调用/访问方式及区别

ContentProvider **不像 Service 有“启动”和“绑定”的概念**，它的生命周期由系统根据访问请求自动触发。外部组件通过 **`ContentResolver`**（内容解析器）结合不同的 `Uri` 类型来调用它。

访问方式主要分为以下维度：

#### 1. 标准 CRUD 操作 vs 自定义方法调用

| 调用方式 | 方法 | 用途 | 返回值 |
|---|---|---|---|
| **标准 CRUD** | `query()`、`insert()`、`update()`、`delete()` | 对数据进行标准的增删改查（最常见） | `Cursor`、`Uri`、`int` |
| **自定义扩展** | `call()` | 执行非 CRUD 的自定义逻辑（如获取数据库版本号、批量事务操作） | `Bundle` |

#### 2. `content://` 协议 vs `file://` 协议

| Uri 类型 | 前缀 | 适用场景 | 关键区别 |
|---|---|---|---|
| **内容 Uri** | `content://` | 访问数据库、内部存储文件（通过 `FileProvider`） | 支持跨应用分享，可控制临时权限 |
| **文件 Uri** | `file://` | Android 7.0（API 24）**之前**用于直接暴露文件路径 | **Android 7.0+ 禁止直接使用** `file://` 跨应用分享文件（会抛出 `FileUriExposedException`），必须改用 `FileProvider` 生成 `content://` |

#### 3. 同步调用 vs 异步调用

| 特性       | 同步调用                             | 异步调用                                                                  |
| -------- | -------------------------------- | --------------------------------------------------------------------- |
| **执行线程** | 调用方所在线程（若在 UI 线程执行耗时查询会卡顿）       | 系统自动在子线程执行                                                            |
| **使用方式** | 直接调用 `ContentResolver.query()` 等 | 使用 `AsyncQueryHandler` 或 `CursorLoader`（已废弃，现在多用 `Room` + `LiveData`） |
| **结果获取** | 方法直接返回结果                         | 通过回调（`onQueryComplete`）获取结果                                           |

#### 4. 权限授予方式

| 权限类型 | 声明方式 | 生效范围 |
|---|---|---|
| **静态权限** | 在 `AndroidManifest.xml` 中声明 `<uses-permission>` 或 `<provider>` 的 `android:readPermission` / `writePermission` | 全局生效，安装时授予 |
| **临时权限** | 在 `Intent` 或 `Uri` 上添加 `FLAG_GRANT_READ_URI_PERMISSION` / `WRITE_URI_PERMISSION` | 仅作用于当前 Intent 或该 Uri，细粒度控制 |

---

### 三、核心区别对比总结

| 对比维度 | CRUD 操作 (`query/insert/update/delete`) | 自定义方法 (`call()`) | `content://` Uri | `file://` Uri |
|---|---|---|---|---|
| **功能范围** | 标准数据操作 | 特殊业务逻辑 | 标准跨进程数据共享 | 文件路径直接暴露（已限制） |
| **跨应用支持** | 支持 | 支持 | 支持（需权限） | 不支持（7.0+ 禁止） |
| **复杂度** | 需实现 `UriMatcher` 匹配 | 自定义参数 `Bundle` 传递 | 结构化数据查询 | 简单文件读写 |
| **安全性** | 较高（权限控制灵活） | 较高 | 高（可加临时权限） | 低（路径泄露风险） |

### 四、具体场景代码实现

以下实现一个简单的 **UserProvider**，用于管理用户数据（基于 SQLite 数据库），并演示外部如何调用。

#### 1. 在 `AndroidManifest.xml` 中声明 Provider

```xml
<provider
    android:name=".UserProvider"
    android:authorities="com.example.myapp.provider"   <!-- 唯一标识 -->
    android:exported="true"                            <!-- 允许外部访问 -->
    android:readPermission="com.example.myapp.READ_USER"
    android:writePermission="com.example.myapp.WRITE_USER" />
```

> 注：`exported="true"` 且声明权限，外部应用需在清单中声明 `<uses-permission>` 才能访问。

#### 2. 实现 ContentProvider 类（核心代码）

```java
public class UserProvider extends ContentProvider {
    private static final String AUTHORITY = "com.example.myapp.provider";
    private static final String TABLE_NAME = "users";
    private static final Uri CONTENT_URI = Uri.parse("content://" + AUTHORITY + "/" + TABLE_NAME);

    // Uri 匹配码
    private static final int USER_DIR = 1;
    private static final int USER_ITEM = 2;
    private static final UriMatcher uriMatcher = new UriMatcher(UriMatcher.NO_MATCH);
    static {
        uriMatcher.addURI(AUTHORITY, TABLE_NAME, USER_DIR);
        uriMatcher.addURI(AUTHORITY, TABLE_NAME + "/#", USER_ITEM); // # 代表数字ID
    }

    private SQLiteDatabase db;

    @Override
    public boolean onCreate() {
        // 注意：运行在 UI 线程，不能做耗时初始化
        db = new UserDBHelper(getContext()).getWritableDatabase();
        return true;
    }

    @Override
    public Cursor query(Uri uri, String[] projection, String selection, String[] selectionArgs, String sortOrder) {
        int code = uriMatcher.match(uri);
        String table = TABLE_NAME;
        if (code == USER_ITEM) {
            // 匹配单条记录，追加 ID 条件
            String id = uri.getLastPathSegment();
            selection = "_id = ?";
            selectionArgs = new String[]{id};
        } else if (code != USER_DIR) {
            throw new IllegalArgumentException("Unknown Uri: " + uri);
        }
        // 实际开发中需注意权限检查（checkReadPermission）
        return db.query(table, projection, selection, selectionArgs, null, null, sortOrder);
    }

    @Override
    public Uri insert(Uri uri, ContentValues values) {
        long id = db.insert(TABLE_NAME, null, values);
        getContext().getContentResolver().notifyChange(uri, null); // 通知数据变化
        return ContentUris.withAppendedId(CONTENT_URI, id);
    }

    @Override
    public int delete(Uri uri, String selection, String[] selectionArgs) {
        int count = db.delete(TABLE_NAME, selection, selectionArgs);
        getContext().getContentResolver().notifyChange(uri, null);
        return count;
    }

    @Override
    public int update(Uri uri, ContentValues values, String selection, String[] selectionArgs) {
        int count = db.update(TABLE_NAME, values, selection, selectionArgs);
        getContext().getContentResolver().notifyChange(uri, null);
        return count;
    }

    @Override
    public String getType(Uri uri) {
        // 返回 MIME 类型，用于 Intent 匹配
        return "vnd.android.cursor.dir/vnd.example.user";
    }

    // 内部辅助数据库类（简化）
    private static class UserDBHelper extends SQLiteOpenHelper {
        public UserDBHelper(Context context) {
            super(context, "user.db", null, 1);
        }
        @Override public void onCreate(SQLiteDatabase db) {
            db.execSQL("CREATE TABLE users (_id INTEGER PRIMARY KEY, name TEXT)");
        }
        @Override public void onUpgrade(SQLiteDatabase db, int oldV, int newV) {}
    }
}
```

#### 3. 外部调用端（Client）示例

```java
// 在 Activity 中通过 ContentResolver 调用
ContentResolver resolver = getContentResolver();
Uri uri = Uri.parse("content://com.example.myapp.provider/users");

// 插入数据
ContentValues values = new ContentValues();
values.put("name", "张三");
resolver.insert(uri, values);

// 查询数据（请在子线程执行）
Cursor cursor = resolver.query(uri, null, null, null, null);
if (cursor != null) {
    while (cursor.moveToNext()) {
        String name = cursor.getString(cursor.getColumnIndex("name"));
        Log.d("Test", "name: " + name);
    }
    cursor.close();
}
```

### 五、实现原理（核心机制）

#### 1. 生命周期与初始化时机
ContentProvider **在 Application 的 `onCreate()` 之前**就会被系统初始化（实例化并调用 `onCreate()`）。这是因为系统需要在应用启动早期准备好数据访问接口，以便其他组件或应用随时调用。

#### 2. 跨进程通信（IPC）原理
- 调用端（Client）通过 `Context` 获取 `ContentResolver`，实际是一个 **`ContentResolver` 的代理对象**。
- 底层通过 **Binder 机制** 向 `ActivityManagerService（AMS）` 请求目标 Provider。
- AMS 查找目标 Provider 是否已运行。若未运行，则创建目标进程、实例化 Provider 并注册到 AMS。
- 随后，AMS 将目标 Provider 的 Binder 引用（`IContentProvider`）返回给调用端。
- 调用端通过该 Binder 引用直接跨进程调用 `query/insert/update/delete` 等方法，数据通过 Binder 的 Parcel 序列化机制进行传输。

#### 3. 数据变化通知机制
当 Provider 中的数据发生变化（如 `insert/update/delete`）时，调用 `getContext().getContentResolver().notifyChange(uri, null)` 会通知系统。所有通过 `ContentResolver.registerContentObserver()` 注册了监听器的组件，都会收到回调，实现类似“观察者模式”的数据联动更新。

### 六、重要补充与注意事项

- **线程安全**：虽然 Provider 方法运行在主线程，但 SQLite 本身支持多线程读，写操作需加锁（通常 `SQLiteDatabase` 内部已做处理）。若在 Provider 内执行耗时 SQL，请自行切换到子线程，但注意不能阻塞 UI 线程。
- **FileProvider 特例**：Android 7.0+ 分享文件时，必须使用 `FileProvider`（继承自 ContentProvider）。它会动态生成 `content://` Uri 并授予临时读写权限，避免 `file://` 带来的安全隐患。
- **Room 集成**：现在 Google 推荐使用 Room 数据库，配合 `RoomContentProvider` 的封装，可以更便捷地实现 Provider，但底层原理和调用方式不变。
- **多进程场景**：若 Provider 设置了 `android:multiprocess="true"`，每个进程会持有自己的 Provider 实例，数据不共享；默认 `false` 时只有一个 Provider 实例运行在宿主进程。

掌握 ContentProvider 的核心在于理解 **Uri 匹配、权限管控、Binder 跨进程通信** 这三者的协作关系。在实际开发中，除非需要跨应用共享复杂数据，否则优先使用 Room + LiveData 满足应用内数据需求。
