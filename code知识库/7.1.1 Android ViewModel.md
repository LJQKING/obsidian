### 一、ViewModel是什么

`ViewModel` 是 Android Jetpack 架构组件中的一个核心类，它的定位是**业务逻辑或屏幕级的状态容器（State Holder）**。

你可以将它理解为 Activity 或 Fragment 的“数据管家”和“业务助理”。它的核心职责是：

- **持有并管理界面状态（UI State）**：将界面所需的数据（如用户列表、加载状态、输入框内容等）存放在 `ViewModel` 中。
- **封装业务逻辑**：将与界面相关的业务逻辑（如数据获取、处理等）从 Activity/Fragment 中剥离，放入 `ViewModel`。
- **生命周期感知**：`ViewModel` 具有生命周期意识，能自动应对屏幕旋转等配置变化。

`ViewModel` 最大的价值在于**解耦**和**状态持久化**。它有效地将“视图”与“数据/逻辑”分离，使得代码更清晰、更健壮，也极大地提升了应用的可测试性。

### 二、核心使用方式及区别

在实际开发中，主要涉及 `ViewModel` 与 `AndroidViewModel` 的区别，以及不同的实例化方式。

#### 1. `ViewModel` vs `AndroidViewModel`：是否需要 `Application` 上下文

这是两者最核心的区别。

| 特性 | `ViewModel` | `AndroidViewModel` |
| :--- | :--- | :--- |
| **继承关系** | 基类 | `ViewModel` 的子类 |
| **上下文** | **无** `Application` 上下文 | **持有** `Application` 上下文 |
| **构造函数** | 无参构造函数 | 必须传入 `Application` 参数 |
| **使用场景** | **绝大多数情况**。不依赖 `Context` 的纯业务逻辑和数据持有 | **需要 `Context` 的特殊情况**。如需要获取系统服务（`Context.getSystemService()`）、使用资源文件（`R.string.xxx`）或实例化 `Repository` 中的数据库 |

> **核心原则**：`ViewModel` 的生命周期可能比 Activity 或 Fragment 更长，**它永远不应该持有 Activity 的引用（如 `this`）**，否则会导致严重的内存泄漏。如果确实需要 `Context`，请使用 `AndroidViewModel`，因为它持有的是 `Application` 上下文，不会造成内存泄漏。

#### 2. 实例化（创建）方式的演进与区别

创建 `ViewModel` 的方式经历了多次演进，主要区别在于**便捷性**和**是否支持构造函数传参**。

| 创建方式 | 示例（Kotlin） | 特点与适用场景 |
| :--- | :--- | :--- |
| **`ViewModelProviders.of()` (已废弃)** | `ViewModelProviders.of(this).get(MyViewModel::class.java)` | 早期方式，内部仍是创建 `ViewModelProvider`，现已不推荐使用。 |
| **`ViewModelProvider(this)` (基础方式)** | `ViewModelProvider(this).get(MyViewModel::class.java)` | 比上一种更直接，减少了不必要的抽象层。 |
| **`by viewModels()` (委托，最推荐)** | `private val viewModel: MyViewModel by viewModels()` | **最简洁、最推荐的方式**。利用 Kotlin 属性委托，在 Activity/Fragment 中一行代码即可完成创建。 |
| **自定义 `Factory`** | `val viewModel by viewModels { MyViewModelFactory("param") }` | **当 `ViewModel` 构造函数需要自定义参数时**，必须使用。通过实现 `ViewModelProvider.Factory` 接口来手动创建实例。 |
| **`CreationExtras` (最新方式)** | 通过 `extras` 获取 `Application` 和自定义参数 | 从 `lifecycle-viewmodel:2.5.0` 开始引入，旨在解决自定义 `Factory` 无法复用的问题，提供了一种更优雅的参数传递方式。 |

### 三、具体场景代码实现

#### 场景一：Activity 中管理界面数据（应对屏幕旋转）

这是 `ViewModel` 最典型的使用场景，用于在屏幕旋转等配置变化时保留数据。

**1. 定义 ViewModel**

```kotlin
// 1. 定义一个 ViewModel 来管理计数器的状态
class CounterViewModel : ViewModel() {
    private val _count = MutableLiveData<Int>()
    val count: LiveData<Int> = _count

    init {
        _count.value = 0
    }

    fun increment() {
        _count.value = (_count.value ?: 0) + 1
    }
}
```

**2. 在 Activity 中使用**

```kotlin
class MainActivity : AppCompatActivity() {

    // 2. 使用 by viewModels() 委托创建 ViewModel
    private val viewModel: CounterViewModel by viewModels()

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContentView(R.layout.activity_main)

        val button = findViewById<Button>(R.id.button)
        val textView = findViewById<TextView>(R.id.textView)

        // 3. 观察数据变化，更新 UI
        viewModel.count.observe(this) { newCount ->
            textView.text = "Count: $newCount"
        }

        button.setOnClickListener {
            // 4. 点击按钮时，修改 ViewModel 中的数据
            viewModel.increment()
        }
    }
}
```

当屏幕旋转时，Activity 会重建，但 `viewModel` 实例会被保留，`count` 的值不会丢失，界面会立即恢复为旋转前的状态。

#### 场景二：多个 Fragment 之间共享数据

`ViewModel` 的作用域可以限定到其宿主 Activity。因此，同一个 Activity 下的多个 Fragment 可以共享一个 `ViewModel` 实例来实现通信。

**1. 定义共享数据的 ViewModel**

```kotlin
// 定义在 Activity 作用域内的 ViewModel，用于 Fragment 间通信
class SharedViewModel : ViewModel() {
    private val _selectedItem = MutableLiveData<String>()
    val selectedItem: LiveData<String> = _selectedItem

    fun selectItem(item: String) {
        _selectedItem.value = item
    }
}
```

**2. 在 Fragment 中使用（以列表Fragment和详情Fragment为例）**

```kotlin
// Fragment A: 列表Fragment，负责更新数据
class ListFragment : Fragment() {
    // 关键：使用 activityViewModels() 获取作用域为宿主 Activity 的 ViewModel
    private val viewModel: SharedViewModel by activityViewModels()

    override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
        super.onViewCreated(view, savedInstanceState)
        // 假设列表项被点击
        itemClickListener = { item ->
            // 更新 SharedViewModel 中的数据
            viewModel.selectItem(item)
        }
    }
}

// Fragment B: 详情Fragment，负责显示数据
class DetailFragment : Fragment() {
    // 同样使用 activityViewModels() 获取同一个 ViewModel 实例
    private val viewModel: SharedViewModel by activityViewModels()

    override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
        super.onViewCreated(view, savedInstanceState)
        // 观察数据变化，更新 UI
        viewModel.selectedItem.observe(viewLifecycleOwner) { item ->
            textView.text = "Selected: $item"
        }
    }
}
```

通过在两个 Fragment 中使用 `by activityViewModels()`，它们获取到的是同一个 `SharedViewModel` 实例，从而实现数据共享。

### 四、实现原理

`ViewModel` 的核心原理围绕 **`ViewModelStore`** 和 **`ViewModelStoreOwner`** 展开。

#### 1. 核心角色

- **`ViewModelStoreOwner`**：一个接口，标识一个类可以“拥有” `ViewModel`。`ComponentActivity` 和 `Fragment` 都实现了这个接口。
- **`ViewModelStore`**：`ViewModel` 的“仓库”，本质是一个 **`HashMap<String, ViewModel>`**，用于存储当前所有者（Owner）持有的所有 `ViewModel` 实例。
- **`ViewModelProvider`**：负责从 `ViewModelStore` 中**获取或创建** `ViewModel` 实例。

#### 2. 工作流程

1.  **获取 Owner**：当你在 Activity 中调用 `by viewModels()` 时，本质上是向当前的 `ViewModelStoreOwner`（即该 Activity）请求一个 `ViewModel`。
2.  **查找或创建**：`ViewModelProvider` 会先根据 `ViewModel` 的类名生成一个 Key，去 Owner 的 `ViewModelStore`（即那个 HashMap）中查找。
    - **如果找到**：直接返回缓存的实例。
    - **如果没找到**：通过 `Factory` 创建一个新的 `ViewModel` 实例，并将其存入 `ViewModelStore` 中，然后返回该实例。
3.  **生命周期管理**：`ViewModelStore` 的生命周期与它的 Owner（Activity/Fragment）绑定。
    - **配置变化时（如屏幕旋转）**：旧的 Activity 会销毁，但系统会保留其 `ViewModelStore`，并将它传递给新的 Activity 实例，因此数据得以保留。
    - **真正销毁时（如用户返回）**：当 Activity 被彻底销毁（非配置变化），系统会调用 `ViewModelStore` 的 `clear()` 方法，遍历并调用其中每个 `ViewModel` 的 `onCleared()` 方法，然后清空存储，完成资源释放。这给了我们在 `ViewModel` 销毁时执行清理工作的机会（如取消网络请求）。

---

### 五、总结

- **ViewModel 是什么**：一个**生命周期感知型**的**屏幕级状态容器**，用于管理 UI 数据和封装业务逻辑。
- **核心区别**：`ViewModel`（无 Context）与 `AndroidViewModel`（有 Application Context）的选择；以及通过 `by viewModels()`（无参）与自定义 `Factory`（有参）等不同实例化方式的适用场景。
- **实现原理**：通过 `ViewModelStoreOwner`（如 Activity）持有的 `ViewModelStore`（一个 Map）来缓存 `ViewModel` 实例。配置变化时实例被保留，真正销毁时才被清除并回调 `onCleared()`。
