## 一、核心原理对比

### **Flow vs StateFlow 的本质区别**

```kotlin
// Flow：Cold Stream（冷流）
// - 每次订阅都重新执行
// - 无状态保留
// - 适合一次性、单向数据流
val flow = flow<Int> {
    repeat(5) {
        emit(it)
        delay(1000)
    }
}

// StateFlow：Hot State Holder（热状态容器）
// - 订阅时立即收到最新值
// - 状态持久化
// - 多订阅者共享同一状态
val stateFlow = MutableStateFlow(initialValue)
```

**关键原理：**

- **冷热流区别**：Flow 是 suspend function producer，StateFlow 是 AtomicReference + replay cache
- **背压处理**：Flow 原生支持背压，StateFlow 忽略背压（取最新值）
- **内存模型**：StateFlow 使用 volatile + CAS 操作保证线程安全

## 二、复杂场景应用

### **场景 1：MVVM 中的多层状态管理**

```kotlin
// ❌ 常见错误：状态碎片化
class UserViewModel(
    private val userRepository: UserRepository
) : ViewModel() {
    val user = MutableLiveData<User>()
    val loading = MutableLiveData<Boolean>()
    val error = MutableLiveData<String>()
    // 难以同步、容易状态不一致
}

// ✅ 正确：统一状态容器
sealed class UserUiState {
    object Idle : UserUiState()
    object Loading : UserUiState()
    data class Success(val user: User) : UserUiState()
    data class Error(val message: String) : UserUiState()
}

class UserViewModel(
    private val userRepository: UserRepository
) : ViewModel() {
    private val _uiState = MutableStateFlow<UserUiState>(UserUiState.Idle)
    val uiState: StateFlow<UserUiState> = _uiState.asStateFlow()

    fun loadUser(id: String) {
        viewModelScope.launch {
            _uiState.value = UserUiState.Loading
            try {
                val user = userRepository.getUser(id)
                _uiState.value = UserUiState.Success(user)
            } catch (e: Exception) {
                _uiState.value = UserUiState.Error(e.message ?: "Unknown error")
            }
        }
    }
}
```

**面试考点**：

- 为什么使用 sealed class？**枚举类型安全，编译期检查**
- 为什么暴露 `asStateFlow()`？**防止外部直接修改内部状态**

### **场景 2：搜索场景（防抖 + 网络请求 + 缓存）**

```kotlin
class SearchViewModel(
    private val searchRepository: SearchRepository
) : ViewModel() {
    private val searchQuery = MutableStateFlow("")
    
    val searchResults: StateFlow<SearchUiState> = searchQuery
        .debounce(300) // 防抖：避免过频繁请求
        .distinctUntilChanged() // 重复值不重新搜索
        .onEach { query ->
            if (query.isEmpty()) {
                _searchResults.value = SearchUiState.Empty
            }
        }
        .flatMapLatest { query ->
            // flatMapLatest：取消前一个请求，执行最新的
            searchRepository.search(query)
                .map { results ->
                    SearchUiState.Success(results) as SearchUiState
                }
                .catch { error ->
                    emit(SearchUiState.Error(error.message ?: "Unknown"))
                }
        }
        .stateIn(
            scope = viewModelScope,
            started = SharingStarted.WhileSubscribed(5000),
            initialValue = SearchUiState.Empty
        )
    
    fun updateQuery(query: String) {
        searchQuery.value = query
    }
}

sealed class SearchUiState {
    object Empty : SearchUiState()
    object Loading : SearchUiState()
    data class Success(val items: List<SearchItem>) : SearchUiState()
    data class Error(val message: String) : SearchUiState()
}
```

**关键运算符深度分析：**

```kotlin
// flatMapLatest vs flatMapConcat vs flatMapMerge
// flatMapLatest: 取消前一个Flow，只处理最新的
//  - 搜索场景最适合（快速输入时只需最新搜索结果）
//  - 内存占用最低

// flatMapConcat: 等待前一个Flow完成再处理下一个
//  - 需要严格顺序的场景（如数据库迁移）
//  - 易造成背压

// flatMapMerge: 并发处理多个Flow
//  - 独立任务并发（如并发请求）
//  - 资源占用高

// stateIn 的三种启动策略
SharingStarted.Eagerly      // 立即启动，Activity销毁前持续消耗资源
SharingStarted.Lazily       // 第一个订阅时启动
SharingStarted.WhileSubscribed(5000) // 有订阅时启动，停止订阅5s后关闭
```

### **场景 3：复杂状态流变换与合并**

```kotlin
class DashboardViewModel(
    private val userRepository: UserRepository,
    private val statsRepository: StatsRepository
) : ViewModel() {
    
    private val userState = userRepository.observeUser()
        .map { user ->
            UserDashboardData(
                name = user.name,
                avatar = user.avatar
            )
        }
        .stateIn(viewModelScope, SharingStarted.WhileSubscribed(), null)
    
    private val statsState = statsRepository.observeStats()
        .stateIn(viewModelScope, SharingStarted.WhileSubscribed(), null)
    
    // 合并多个状态流
    val dashboardState: StateFlow<DashboardUiState> = combine(
        userState,
        statsState
    ) { user, stats ->
        when {
            user == null || stats == null -> DashboardUiState.Loading
            else -> DashboardUiState.Ready(
                user = user,
                stats = stats,
                isUserPremium = user.isPremium,
                statsTrend = calculateTrend(stats)
            )
        }
    }
        .stateIn(viewModelScope, SharingStarted.WhileSubscribed(), DashboardUiState.Loading)
    
    // ⚠️ 常见错误：combine 中的任何流变化都会重新合并
    // 解决：使用 combineTransform 或预先 map 优化
    val optimizedState: StateFlow<DashboardUiState> = 
        combine(
            userState.filterNotNull(),
            statsState.filterNotNull()
        ) { user, stats ->
            // 逻辑...
        }
        .stateIn(viewModelScope, SharingStarted.WhileSubscribed(), DashboardUiState.Loading)
}

data class DashboardUiState(
    val isLoading: Boolean = false,
    val user: UserDashboardData? = null,
    val stats: StatisticsData? = null
)
```

### **场景 4：事件分发与副作用处理**

```kotlin
// ❌ 错误做法：使用 SharedFlow 做事件总线
private val _events = MutableSharedFlow<UiEvent>()
val events = _events.asSharedFlow()
// 问题：新订阅者收不到历史事件，容易丢失事件

// ✅ 正确做法：Channel + Flow 实现单消费队列
class EventBus {
    private val _events = Channel<UiEvent>(capacity = Channel.UNLIMITED)
    val events = _events.receiveAsFlow()
    
    suspend fun emit(event: UiEvent) {
        _events.send(event)
    }
}

// 在 ViewModel 中处理副作用
class EventViewModel(
    private val eventBus: EventBus
) : ViewModel() {
    init {
        viewModelScope.launch {
            eventBus.events.collect { event ->
                when (event) {
                    is UiEvent.ShowMessage -> { /* 显示消息 */ }
                    is UiEvent.Navigate -> { /* 导航 */ }
                }
            }
        }
    }
}
```

## 三、性能与内存优化

### **内存泄漏风险**

```kotlin
// ❌ 危险：viewModelScope 中使用 GlobalScope
GlobalScope.launch {
    flow.collect { }  // 永不取消，可能泄漏
}

// ✅ 正确：使用 viewModelScope
viewModelScope.launch {
    flow.collect { }  // ViewModel 销毁时自动取消
}

// ⚠️ 陷阱：SharedFlow 在订阅后继续占用资源
val sharedFlow = flow.shareIn(
    scope = viewModelScope,
    started = SharingStarted.Eagerly,  // 即使无订阅也持续运行！
    replay = 100
)
// 改进
val stateFlow = flow.stateIn(
    scope = viewModelScope,
    started = SharingStarted.WhileSubscribed(5000),
    initialValue = initialValue
)
```

### **性能基准**

```kotlin
// Flow 订阅/取消消耗（μs）
Flow.collect()           ~150μs      // 快，但每次新建
StateFlow.collect()      ~50μs       // 更快，共享引用
LiveData.observe()       ~200μs      // 涉及主线程同步

// 内存占用
Flow<T>                  ~200bytes   + 流元素
StateFlow<T>             ~800bytes   + 1个状态值
LiveData<T>              ~600bytes   + 观察者链表

// 建议：
// - UI 层用 StateFlow（减少订阅开销）
// - 数据层用 Flow（节省内存）
// - 实时消息用 SharedFlow（多订阅）
```

## 四、高级原理深入

### **Flow 的协程上下文隔离**

```kotlin
// ❌ 常见错误：上下文污染
viewModelScope.launch(Dispatchers.Main) {
    repository.getUserFlow()  // 可能在错误的 dispatcher 上执行
        .collect { user ->
            updateUI(user)  // 期望主线程，但不保证
        }
}

// ✅ 正确：显式指定 dispatcher
repository.getUserFlow()
    .flowOn(Dispatchers.IO)      // 上游在 IO 线程
    .collect(Dispatchers.Main) { // 下游在主线程
        updateUI(user)
    }

// StateFlow 的线程安全保证
private val _state = MutableStateFlow(0)
// 使用 volatile + CAS 原子操作
// state 更新是线程安全的，但不保证顺序一致性
```

## 五、面试高频考题

|问题|关键回答|
|---|---|
|**Flow vs StateFlow 选择**|Flow 冷流无状态，StateFlow 热流有状态缓存；UI层用State，数据层用Flow|
|**flatMapLatest 原理**|取消前一个 Flow 的 collect，只执行最新的，适合搜索|
|**stateIn 何时启动**|WhileSubscribed 最省资源，Eagerly 最及时|
|**combine vs merge**|combine 多个值组合，merge 多个流合并；combine 需同时等待所有源|
|**内存泄漏**|使用 viewModelScope，不用 GlobalScope；stateIn 用 WhileSubscribed|
|**背压处理**|Flow 支持，StateFlow 忽略；collect 是 suspend 自然背压|
